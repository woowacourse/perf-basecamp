## `getTotalLength()`가 트레이스에서 사라졌다

CPU 프로파일에 **함수 노드 자체가 없다.** 6x 스로틀링에서 1회 4.25ms짜리 호출이 한 번이라도 있었다면 샘플에 반드시 잡힌다.

프로파일에 남은 앱 함수는 이게 전부다.

| 함수             | self time                 |
| ---------------- | ------------------------- |
| `handleScroll`   | 1.8ms (384회, 0.005ms/회) |
| `drawPath`       | **0.0ms**                 |
| `getTotalLength` | **노드 없음 = 0회 호출**  |

개선 전 `drawPath`의 내역과 비교하면 이렇다.

| 항목                               | 개선 전 run1 | 개선 후   |
| ---------------------------------- | ------------ | --------- |
| `getTotalLength` (drawPath 안)     | 972ms        | **0ms**   |
| `getTotalLength` (strokeDasharray) | 797ms        | **0ms**   |
| `drawPath`                         | 183ms        | **0.0ms** |
| `setAttribute`                     | 64ms         | 0ms       |

## 스크롤 구간 JS 61.3ms — 개선 전의 1/36

| 항목         | 개선 전 run1 (4.09s) | **개선 후 (5.55s)** |
| ------------ | -------------------- | ------------------- |
| 구간 JS 합계 | **2,223ms**          | **61.3ms**          |

남은 61.3ms의 출처다.

| 출처                                      | 시간      | 비고                                               |
| ----------------------------------------- | --------- | -------------------------------------------------- |
| `requestAnimationFrame` (네이티브 호출)   | 42.8ms    | 384회 × 0.11ms. rAF 스로틀을 쓰면서 새로 생긴 비용 |
| React 이벤트 시스템                       | 12.3ms    | `dispatchContinuousEvent` 등                       |
| **앱 코드 (`handleScroll` + `drawPath`)** | **1.8ms** | scroll 1건당 0.005ms                               |
| 기타 네이티브                             | 4.4ms     |                                                    |

rAF 호출이 앱 코드보다 24배 크지만, 구간 전체(5,546ms)의 0.8%라 문제되지 않는다.

## 강제 동기 스타일 재계산 0회

개선 전 run1은 scroll 1건당 0.991회였다. 개선 후는 **0회다.**

구간의 `Recalculate Style` 505회를 전부 역추적한 결과, **503회가 `PageAnimator::serviceScriptedAnimations`** 에서 나온다. `CustomCursor`의 `wave-text` CSS 애니메이션이며 스크롤과 무관하다(기준선에서도 같은 값).

| 항목                                   | 개선 전 run1 | 개선 후                             |
| -------------------------------------- | ------------ | ----------------------------------- |
| scroll 핸들러 안의 `Recalculate Style` | 226회        | **0회**                             |
| rAF 콜백 안의 `Recalculate Style`      | —            | **0회**                             |
| 구간 `Recalculate Style` 총계          | —            | 505회 (91.1/s, 전부 CSS 애니메이션) |

스크롤 핸들러가 레이아웃 값을 한 번도 읽지 않으므로 끌어올 재계산 자체가 없다.

## 결과가 바뀌지 않으면 아무 일도 하지 않는다

rAF 콜백 383개 중 **363개(95%)가 0.05ms 미만**이다. `clamp` 결과가 직전과 같아 `setState` 없이 끝난 경우다. 나머지 20개만 실제로 렌더를 유발했고 중앙값은 0.976ms다.

구간 `Paint`는 20회로, 값이 실제로 바뀐 횟수와 일치한다.

> 이 비율 자체는 스크롤 범위에 따라 달라지므로 개선 전(24.9%)과 직접 비교하지 않는다. 확인한 것은 "값이 같으면 렌더까지 가지 않는다"가 실제로 동작한다는 사실이다.

## 파이프라인

개선 전:

```
scroll 1건 (초당 61~85회)
  ├ handleScroll → drawPath
  │    ├ offsetTop / offsetHeight 읽기 → 강제 Recalculate Style  (0.43ms)
  │    └ getTotalLength()                                        (4.25ms)
  └ setStrokeOffset → React 렌더 (별도 태스크)
       └ AnimatedPath 렌더 → getTotalLength()                    (4.25ms)
                                                    합계 scroll 1건당 12.6ms
```

개선 후:

```
scroll 1건
  └ handleScroll → rAF 예약만                                    (0.005ms)

rAF 콜백 (프레임당 1회)
  └ drawPath — ref에 저장된 값으로 산술 계산만                    (0.0ms)
       └ 값이 바뀔 때만 setStrokeOffset → React 렌더
                                                    합계 scroll 1건당 2.41ms
```

## 기준선 (정지 구간, 250ms ~ 스크롤 시작 전 1.66s)

| 항목                | 개선 전 run2 | 개선 후 |
| ------------------- | ------------ | ------- |
| 메인 스레드 점유    | 13.4%        | 20.9%   |
| `Recalculate Style` | 67.2/s       | 45.7/s  |
| `Layout`            | 8회          | **0회** |
| `Paint`             | 16회         | **0회** |
| `mousemove`         | 13회         | 28회    |

기준선의 `Layout`/`Paint`가 0이 된 것은 S1 개선(`style.top`/`left` → `transform`) 효과다. 점유율이 20.9%로 높은 것은 이 구간에 페이지 초기 로드와 `mousemove` 28건이 섞였기 때문이다.

**스크롤 구간 점유(16.7%)가 기준선(20.9%)보다 낮다.** 스크롤이 더 이상 추가 부하를 만들지 않는다는 뜻이다.
