## 원인 1 — `getTotalLength()`가 스크롤 구간 JS의 80~86%다

CPU 프로파일 self time 상위다. 3회 모두 같은 그림이다.

| 함수 | run1 | run2 | run3 |
| --- | --- | --- | --- |
| **`getTotalLength`** | **1,765ms (79.4%)** | **1,106ms (85.9%)** | **689ms (83.9%)** |
| `drawPath` | 183ms (8.3%) | 48ms (3.7%) | 34ms (4.2%) |
| `setAttribute` | 64ms (2.9%) | 43ms (3.3%) | 27ms (3.3%) |
| 그 외 전부 | 211ms (9.5%) | 90ms (7.0%) | 71ms (8.6%) |
| (구간 JS 합계) | 2,223ms | 1,287ms | 821ms |

`getTotalLength()`는 **호출 지점이 두 곳**이고, 둘 다 스크롤할 때마다 다시 돈다.

| 호출 지점 | run1 | run2 | run3 | 호출 1회 비용 |
| --- | --- | --- | --- | --- |
| `AnimatedPath.tsx:28` — `drawPath` 안 | 972ms | 672ms | 406ms | 4.24 / 4.25 / 4.37ms |
| `AnimatedPath.tsx:47` — `strokeDasharray` 속성값 | 797ms | 438ms | 287ms | (렌더마다 1회) |

**호출 1회 비용이 4.24 / 4.25 / 4.37ms로 3회 모두 같다.** 6x 스로틀링 기준 프레임 예산(8.33ms)의 절반이 이 호출 하나에 들어간다.

`path`의 `d` 속성은 세그먼트 수백 개짜리 곡선이고, 값은 **처음부터 끝까지 상수다**. 그런데 스크롤 이벤트마다 다시 계산한다.

React 렌더 비용도 사실상 전부 이것이다. `AnimatedPath` 렌더가 하는 일 중 `getTotalLength()`를 뺀 나머지는 run2에서 6ms(JS의 0.5%)다. **컴포넌트 렌더가 무거운 게 아니라, 렌더할 때마다 상수를 다시 재는 것이 무겁다.**

```
scroll 1건
  ├ handleScroll → drawPath                     (bundle.js:10308)
  │    ├ wrapper.offsetTop / offsetHeight 읽기
  │    │    └ 강제 Recalculate Style             (0.43ms)
  │    └ getTotalLength()                        (4.25ms)   ← ①
  └ setStrokeOffset → React 렌더 (별도 태스크)
       └ AnimatedPath 렌더
            └ getTotalLength()                   (4.25ms)   ← ②
```

②는 scroll 이벤트당 1회보다 조금 적다(추정 0.65~0.82회). 히어로 구간처럼 `clamp` 결과가 직전과 같으면 `setStrokeOffset`이 리렌더를 건너뛰기 때문이다.

## 원인 2 — 강제 동기 스타일 재계산 (절차 문서의 가설은 절반만 맞다)

`measure-performance.md` §S2는 `getTotalLength()`와 `offsetTop` 읽기에서 **강제 동기 레이아웃**(`Forced reflow`)이 나올 것으로 봤다. 실측은 다르다.

| 항목 | 실측 |
| --- | --- |
| 강제 **Layout** | **3회 모두 0회** (구간 내 `Layout` 자체가 0) |
| 강제 **Recalculate Style** | scroll 1건당 0.991 / 0.500 / 0.591회 |
| 강제 Recalculate Style 비용 | 중앙값 0.43ms, `drawPath` 총 시간의 4.6~11.9% |

`strokeDashoffset`은 Layout을 유발하지 않으므로 스크롤 중 레이아웃 트리는 계속 깨끗하다. 그래서 강제 Layout은 아예 일어나지 않는다. 반면 `wave-text`가 매 프레임 스타일을 더럽히므로, `drawPath`의 `offsetTop` 읽기가 그 스타일 재계산을 동기로 끌어온다.

**회차별 편차(0.99 vs 0.50 vs 0.59)는 코드가 아니라 입력 방식 때문이다.** `handleScroll` 직전에 스타일 재계산이 이미 돌았다면 스타일이 깨끗해서 강제 재계산이 필요 없다. 강제 재계산이 없었던 케이스를 역추적하면 직전 재계산의 출처가 나온다.

| 회차 | 강제 있음 / 없음 | "없음"의 직전 재계산 출처 | 직전 재계산과의 간격 |
| --- | --- | --- | --- |
| run1 (휠) | 226 / 2 | 입력 핸들러 | 2.22ms |
| run2 (키 리피트) | 79 / 78 | 렌더링 라이프사이클 54, `keydown` 핸들러 24 | 1.61ms |
| run3 (키 단발) | 54 / 38 | 렌더링 라이프사이클 38 | 1.00ms |

키보드 스크롤은 스크롤 이벤트가 라이프사이클의 스타일 재계산 **뒤에** 디스패치되는 프레임이 많아 절반은 강제 재계산이 생략된다. 휠은 그 앞에 들어가 거의 매번 강제 재계산을 만든다.

→ **판정: 읽기/쓰기 분리로 고칠 대상은 맞지만 비용의 주범은 아니다. 88% 이상은 `getTotalLength()`다.** 이 지표는 입력 방식에 좌우되므로 개선 전후 비교 지표로 쓰지 않는다.

## 원인 3 — 화면에 아무것도 안 그려지는 구간에서도 핸들러가 전부 돈다

스크린샷으로 선이 그려지기 시작하는 시점을 확인했다(±100ms).

| 회차 | 선 시작 시점 | 히어로 구간 scroll | 히어로 구간 `drawPath` 시간 |
| --- | --- | --- | --- |
| run1 | ~2,050ms | 57 / 229 (24.9%) | 279ms / 1,165ms |
| run2 | ~3,000ms | 49 / 158 (31.0%) | 235ms / 739ms |
| run3 | ~2,450ms | 22 / 93 (23.7%) | 106ms / 451ms |

히어로 구간에서는 `scrollRatio < 0`이라 `clamp`가 항상 `pathLength`를 돌려준다. 화면은 그대로인데 `getTotalLength()`와 강제 스타일 재계산은 그대로 돈다. **스크롤 핸들러 비용의 약 1/4이 결과가 바뀌지 않는 계산이다.**

## 원인 4 — 스크롤 리스너가 렌더마다 재등록된다

`useScrollEvent(drawPath)`의 `useEffect` 의존성이 `[onScroll]`인데 `drawPath`는 렌더마다 새로 만들어지는 함수다. 따라서 `AnimatedPath`가 리렌더될 때마다 `removeEventListener` → `addEventListener`가 다시 실행된다(run3 self time에 `removeEventListener` 4ms가 잡힌다).

**비용 자체는 JS의 0.5% 미만으로 작다.** 다만 `drawPath`가 매 렌더 새 함수라는 사실은 메모이제이션을 막으므로 개선 시 같이 처리한다.

## Layout Shift — 스크롤은 원인이 아니다

**3회 모두 스크롤 구간의 Layout Shift는 0건이다.** 같은 구간의 `mousemove`도 0건이다. `strokeDashoffset` 애니메이션은 시프트를 만들지 않는다.

시프트는 3회 모두 마우스가 움직인 구간에서만 찍혔고, 시프트 노드도 동일하다.

```
DIV class='...' (194x32)  +  ::before (48x48)
```

`CustomCursor.module.css`의 `.cursor`와 `.cursor::before`다. S1의 원인(`style.top`/`left`)이며 S2 행에는 쓰지 않는다.

다만 기록해 둘 값이 있다.

| 항목 | run1 | run2 | run3 |
| --- | --- | --- | --- |
| 트레이스 전체 시프트 | 54건 | 9건 | 4건 |
| `had_recent_input` | 전부 `false` | 6건 `false` / 3건 `true` | 전부 `false` |
| **녹화 종료 시점 누적 CLS** | **0.0638** | **0.1975** | **0.2077** |

`mousemove`는 CLS 제외 대상 입력이 아니므로 이 시프트는 **점수에 그대로 들어간다.** 재방문 없이 누적 CLS가 0.064 → 0.208까지 올라갔다. 로드 구간만 재는 Lighthouse CLS로는 잡히지 않는 값이고, "나쁨" 기준 0.1을 이미 넘었다. TODO 4번 "Layout Shift 없이 애니메이션이 일어나야 한다"에 정면으로 걸린다.

## 프레임 — 완전 드롭보다 부분 프레임이 문제다

| 항목 | run1 (휠) | run2 (키 리피트) | run3 (키 단발) |
| --- | --- | --- | --- |
| Dropped Frame (빨강) | 3 | 0 | 1 |
| Partially Presented (노랑) | 0 | 94 | 44 |
| **연속 스크롤 1초당 partial** | **0.0** | **41.2** | **40.2** |

절차 문서가 지정한 키보드 스크롤(run2 · run3)에서 **연속 스크롤 1초당 부분 프레임이 40개씩** 발생한다. 120Hz에서 초당 120프레임 중 **약 1/3이 부분 프레임**이라는 뜻이다. 두 회차의 값이 41.2 / 40.2로 거의 같아 재현성이 있다.

run1만 partial 0 / 완전 드롭 3으로 모양이 다르다. 입력 방식과 뷰포트(1728×1460 vs 3090×1556)가 달라 컴포지터 쪽 부담이 다르기 때문으로 보인다. **리포트에는 절차대로 측정한 run2 기준을 쓴다.**

50ms를 넘는 Long Task는 앱 코드 기준 3회 모두 0개다. 대신 7.5~8ms짜리 태스크가 프레임 예산(8.33ms)을 꽉 채운 채 끊이지 않고 이어진다. 연속 스크롤 중 메인 스레드 점유는 79.5 / 87.0 / 94.3%다.

→ 판정 분기는 "Long Task" 쪽이 아니다. **"매 스크롤 이벤트마다 프레임 예산을 채우는 고정 비용이 붙는다"** 쪽이다.

## 프레임 예산 대비 (8.33ms)

| scroll 이벤트를 포함한 태스크 | 중앙값 기준 | 예산 대비 |
| --- | --- | --- |
| 중앙값 | 7.70ms | **92%** |
| p95 | 9.40ms | **113%** |
| `getTotalLength()` 1회만 | 4.25ms | **51%** |

여기에 React 렌더가 **별도 태스크로** 추가된다. `scroll` 이벤트 1건이 메인 스레드에 만드는 총 부하는 **12.6ms**(중앙값)로 프레임 하나를 통째로 넘긴다. 연속 스크롤 중 점유 87%가 여기서 나온다.

## 남은 측정 결함 — 입력 방식과 창 크기가 회차마다 다르다

CPU 스로틀링은 3회 모두 6x로 맞았다. 남은 문제는 아래 둘이다.

| 회차 | 입력 | 근거 | 뷰포트 |
| --- | --- | --- | --- |
| run1 | 휠/트랙패드 | `wheel` 289건, `keydown` 0건 | 1728×1460 |
| run2 | `↓` 키 리피트 (절차 준수) | `keydown` 66 / `keyup` 2, 공백 0회 | 3090×1556 |
| run3 | `↓` 단발 7회 | `keydown` 7 / `keyup` 7, 150ms 넘는 공백 6회(합 2.91s) | 3090×786 |

- **run1**은 절차 문서 §S2 "하지 말 것"의 휠 스크롤이다.
- **run3**은 키를 누른 채 유지하지 않고 7번 눌렀다 뗐다. 스크롤이 끊겨 구간의 73%가 공백이다.
- **뷰포트가 3회 모두 다르다.** `window.innerHeight`가 `drawPointY` 계산에 직접 들어가고 페인트 면적도 달라진다. run3(786px)은 `↓` 한 번의 스크롤 비중이 커서 이벤트 빈도가 85.0/s까지 올라갔다.

이벤트 1건당 비용(`getTotalLength` 4.24~4.37ms, `drawPath` 중앙값 4.66~5.11ms, scroll 태스크 중앙값 7.51~8.04ms)은 이 차이에도 흔들리지 않았다. **그래서 이번 지표는 살렸다.** 다만 프레임 수와 강제 스타일 재계산 비율은 회차별로 갈렸다.

### 개선 후 측정할 때 맞출 것

- **3회 모두 같은 창 크기**로 잰다. DevTools 도킹 위치까지 고정한다.
- 히어로 빈 공간 클릭 → `↓`를 **누른 채 5초 유지**. 휠·단발 입력 금지. run2가 유일하게 절차를 지켰지만 2.28s로 짧다.
- 녹화 직전마다 CPU 6x가 걸려 있는지 확인한다.
- 녹화 시작 직후 ~190ms의 프로파일러 부착 태스크는 무시하고 250ms 이후부터 센다.

## 비교 지표 선택

초당 횟수는 쓸 수 없다. 스크롤 속도·입력 방식·뷰포트에 그대로 비례한다(61.3 ~ 85.0/s).

아래 네 개는 3회 값이 서로 가까워 **입력 방식과 창 크기가 달라도 흔들리지 않는다.** 개선 전후 비교는 이것으로 한다.
