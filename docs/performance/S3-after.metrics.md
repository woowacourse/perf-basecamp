## 트랜지션이 동작한다

`Animation` 이벤트가 10건 찍혔고 전부 `displayName: "transform"`이다.

| 항목             | 값                                     |
| ---------------- | -------------------------------------- |
| 전환 건수        | 10 (호버 상태 변화 수와 일치)          |
| 지속 시간        | 197.2 ~ 212.5ms, **중앙값 203.2ms**    |
| 대상 노드        | `DIV .gifItem` 2개 (`nodeId` 4430, 4431) |
| 전환 중 `Layout` | **0회**                                |
| 전환 중 `Paint`  | **0회**                                |

선언한 0.2초가 실측 203.2ms로 나왔으므로 `auto → <length>` 때문에 보간이 시작조차 못 하던 상태는 해소됐다. 200ms 동안 메인 스레드가 하는 일은 프레임마다 `elementCount: 1`짜리 스타일 재계산 한 번뿐이고 중앙값이 0.048ms라, 전환 한 건이 도는 내내 드는 비용이 약 0.9ms다.

전환이 돌지 않는 구간에서는 `Recalculate Style`이 0이다. 151회 중 135회가 전환 진행 구간에 몰려 있고 나머지가 상태 변화 순간에 찍힌 것이라, 개선 전 0.92에서 15.1로 늘어난 재계산은 없던 애니메이션이 생기면서 치르는 값이다.

## Layout Shift가 사라졌다

**트레이스 전체에 `LayoutShift` 이벤트가 0건이다.** 개선 전에는 변화 1회당 정확히 1건이 `had_recent_input: false`로 찍혀 CLS에 100% 가산됐고, 카드 5개를 한 번씩 훑을 때마다 +0.0068씩 쌓였다.

`transform`은 요소의 레이아웃 박스를 건드리지 않으므로 카드가 12px 올라가도 시프트로 기록되지 않는다. TODO 4번의 "Layout Shift 없이 애니메이션이 일어나야 한다"를 충족한다.

## 남은 문제 1 — `Layout`이 변화 1회당 1회 그대로다

목표는 0이었으나 10회 그대로다. 다만 발생 위치와 성격이 달라졌다.

`InvalidateLayout`이 트레이스에 10건 있고 전부 `nodeId: 2046`(`#document`)이며 `stackTrace`가 없다. 시각을 전환 이벤트와 맞춰 보면 규칙이 뚜렷하다.

| 시점                          | 건수 | 함께 찍히는 것                                              |
| ----------------------------- | ---- | ----------------------------------------------------------- |
| **진입 전환이 시작될 때**     | 5    | `Layout`(dirtyObjects 8) + `Paint` 3개 + `Layerize`         |
| **이탈 전환이 끝날 때**       | 5    | `Layout`(dirtyObjects 9) + `Paint` 2개 + `Layerize`         |
| 전환이 도는 200ms 동안        | 0    | 스타일 재계산만                                             |

진입 시작에서 `.gifItem`이 무한 클립(`-8388608 ~ 8388607`)으로 따로 페인트되고, 이탈 종료에서 `transitionend` 직후 해당 페인트가 사라지며 `#document`와 `HTML`만 다시 칠해진다. 카드가 자기 레이어로 승격됐다가 문서 레이어로 되돌아오는 왕복이 보이고, 그 두 경계에서만 문서 레이아웃이 더러워진다.

`transform`이 `none`과 `translateY` 사이를 오가는 것이 두 경계의 공통점이다. `none`이 아닌 `transform`은 요소를 stacking context이자 포함 블록으로 만들기 때문에, 값이 `none`을 넘나들 때마다 Blink가 문서 레이아웃을 다시 잡는다고 읽힌다.

→ **`.gifItem`에 `transform: translateY(0)`을 기본값으로 선언하면** 전환이 `translateY(0) → translateY(-0.75rem) → translateY(0)`으로 돌면서 `none`을 한 번도 거치지 않는다. 남은 `Layout` 10회와 `Paint` 25개가 사라지는지 재측정으로 확인해야 한다.

`Paint`가 5.0에서 2.5로 준 것도 같은 맥락이다. 개선 전에는 변화마다 `#document`, `.gifItem`, `.gifImage`, `.gifTitleBg`, `.gifTitle` 5개를 칠했는데, 이제 진입에서 3개(`#document`, `HTML`, `.gifItem`), 이탈에서 2개(`#document`, `HTML`)만 칠한다.

## 남은 문제 2 — Partially Presented가 0.67에서 1.50으로 늘었다

| 항목                  | 개선 전 (중앙값) | 개선 후               |
| --------------------- | ---------------- | --------------------- |
| Partial 총 개수       | 7                | **15**                |
| 변화 1회당            | 0.67             | **1.50**              |
| 전환 경계에서 발생    | 100%             | **15/15 (100%)**      |
| `frame_type`          | 전건 `FORKED`    | **전건 `FORKED`**     |
| `affects_smoothness`  | 전건 `false`     | **전건 `false`**      |

15건 전부 전환의 시작 또는 종료 시각에 걸쳐 있다. 개선 전에는 메인 업데이트가 변화 1회당 한 번(12px 점프)이었는데 이제 승격과 반납으로 두 번 생기므로, 경계 20개 중 15개에서 컴포지터 프레임이 갈라진 것이다.

`affects_smoothness`가 15건 모두 `false`라 사용자가 체감하는 끊김으로 집계되지는 않지만, TODO 4번의 "Partially Presented Frame 역시 최소로 발생해야 한다"는 아직 위반이다. 원인이 위의 `Layout`과 같은 승격·반납 왕복이므로 `transform: translateY(0)` 기본값이 함께 해결할 후보다.

GPU 점유가 44%에서 12%로 떨어졌고 Dropped Frame도 3.8%에서 1.1%로 줄었지만, **CSS 수정의 효과가 아니다.** 뷰포트가 좁아져 그리드가 2열이 되면서 화면에 동시에 보이는 GIF 수가 줄었고 `Decode Image` 빈도도 1/2 이하로 떨어졌다. Dropped 6건 중 5건은 `BACKFILL`이고 전환 구간 밖에서 발생했으므로, 개선 전 문서의 결론대로 GIF 재생 부하이며 TODO 1번 범위다.

동일 조건 비교가 필요하면 production 빌드와 같은 창 크기로 다시 재야 한다.

## 다음 조치
