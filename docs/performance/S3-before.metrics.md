## 결론 먼저

`transition: all 0.2s ease-in`은 **한 번도 동작하지 않는다.** `.gifItem`에 `top` 기본값이 없어(`auto`) 호버 시 `-0.75rem`으로 보간이 불가능하고, 카드는 12px을 **한 프레임에 그냥 점프한다.**

6x 환경에서 새로 드러난 사실이 하나 있다. **호버 태스크 중앙값이 8.56ms로 120Hz 프레임 예산(8.33ms)을 넘는다.** 1x에서는 1.08ms라 예산 대비 13%였는데, 스로틀링을 걸자 호버 1회가 프레임 하나를 통째로 잡아먹는다. 10회 중 6회가 예산을 초과했고, 그 결과가 Partially Presented Frame이다.

- 호버 상태 변화 1회 = `Layout` 1회 + `Paint` 5개 + Layout Shift 1건 (`had_recent_input: false` → **CLS에 그대로 가산**)
- Partially Presented Frame은 **3회 모두 100% 호버 프레임에서만** 발생한다
- Dropped Frame은 호버와 무관하다. 기준선 구간이 오히려 더 높다(4.9% vs 3.8%). 16개 GIF 동시 재생으로 GPU 프로세스가 상시 44% 점유된 결과다

## 원인 1 — `transition`이 동작하지 않는다. 카드는 12px을 점프한다

절차 문서 §S3는 "진입·이탈 시점마다 **0.2초 길이의** `Recalculate Style` + `Layout` 반복 구간이 생긴다"고 예상했다. 실측은 정반대다.

| 절차 문서 예상 | 실측 |
| --- | --- |
| 진입·이탈마다 0.2초간 매 프레임 `Layout` | **상태 변화 1회당 `Layout` 1회** |
| 120Hz 기준 변화당 약 24프레임 | **1프레임** |

근거는 세 가지다.

1. **`Layout` 횟수가 상태 변화 횟수를 넘지 않는다.** 3회 모두 `Layout` ≤ 변화 수이고, 부족분은 두 변화가 한 프레임에 겹친 경우로 전부 설명된다.
2. **Layout Shift의 이동량이 한 번에 24 device px(= 12 CSS px)다.** 3회 34건 전부 `frame_max_distance: 24`다. 0.2초에 걸쳐 보간됐다면 1px 남짓씩 20여 건으로 쪼개져 찍힌다.
3. **`Recalculate Style`의 `elementCount`가 1이다** (겹친 프레임만 2). 트랜지션이 돌고 있다면 매 프레임 같은 요소가 다시 계산된다.

원인은 CSS에 있다.

```css
/* GifItem.module.css */
.gifItem {
  position: relative;
  transition: all 0.2s ease-in;   /* 12행 — top 기본값이 없다 */
}
.gifItem:hover {
  top: -0.75rem;                  /* 17행 — auto → -12px */
}
```

`.gifItem`에 `top`이 선언돼 있지 않으므로 계산값은 `auto`다. `auto`와 `<length>`는 보간할 수 없어 트랜지션이 시작되지 않는다. `transition: all 0.2s ease-in`은 **선언만 있고 대상이 없는 상태**다.

→ 개선 목표는 "애니메이션을 가볍게"가 아니라 **"없던 애니메이션을 만들되 Composite 단계로 만들기"** 다.

### 주의 — `top: 0`을 추가하는 방향은 24배 악화다

`.gifItem`에 `top: 0`만 넣으면 트랜지션이 비로소 동작하는데, `top`은 Layout 트리거다.
그러면 상태 변화 1회당 `Layout`이 1회에서 **0.2초 × 120Hz ≈ 24회**로 늘고 Layout Shift도 같은 배수로 늘어난다.
6x 환경에서 호버 태스크가 이미 8.56ms로 프레임 예산을 넘고 있으므로, 이 방향은 프레임을 확실히 무너뜨린다.
**`top` → `transform: translateY(-0.75rem)`으로 바꾸는 것이 유일하게 맞는 방향이다.**

진입은 위로, 이탈은 아래로 정확히 교대한다. `impacted_nodes`는 해당 카드 `div` 뿐이고, `position: relative` 오프셋이라 형제 카드는 밀리지 않는다.

**`had_recent_input`이 전부 `false`인 점이 핵심이다.** 마우스 이동·호버는 CLS 제외 대상 입력(클릭·탭·키 입력)이 아니므로 **이 시프트는 CLS 점수에 100% 가산된다.**

**카드 5개를 한 번씩 훑는 것만으로 CLS +0.0068이다**(run2 기준). 카드 1개를 호버할 때마다(진입+이탈 2건) 약 +0.0014씩 계속 쌓인다.

누적값 0.6618 → 0.6685 → 0.6769는 문서 시작부터의 **원시 누적 합계**(세션 윈도 적용 전)다. 회차 간 증가분이 각 회차의 구간 합과 정확히 일치한다(0.6685 − 0.6618 = 0.0067 = run2 합). Home → Search가 클라이언트 라우팅이라 문서가 바뀌지 않아, 측정 세션 내내 한 번도 리셋되지 않고 계속 쌓였다.

`FORKED`는 컴포지터가 이미 자기 쪽 업데이트(GIF 프레임)를 진행 중인데 메인 스레드 업데이트(카드 점프)가 끼어들어 표면이 갈라진 경우다.

6x에서 이 수치가 더 잘 설명된다. **호버 태스크 중앙값이 8.56ms로 120Hz 프레임 예산 8.33ms를 넘는다.** 10회 중 6회가 예산 초과이고(최대 14.24ms), 예산을 넘은 메인 업데이트가 이미 진행 중인 컴포지터 프레임에 도착하면서 프레임이 반쪽만 올라간다. 변화 1회당 0.67이라는 값이 "예산 초과율 55%"와 같은 자릿수다.

→ **TODO 4번의 "Partially Presented Frame 역시 최소로 발생해야 한다"는 현재 위반 상태이고, 원인이 호버로 단독 확정된다.**

## 다음 측정 때 확인할 것

- 절차 문서 §S3의 "첫 줄 카드 1→5"는 **1행이 4개뿐이라 불가능하다.** "1행 4개 + 2행 1개"로 문서를 고친다.
- **카드 경계에서 멈추지 않는다.** run1에서 포인터가 경계에 걸려 3ms 간격의 진입·이탈이 4회 더 찍혔다.
- **같은 카드를 반복 호버하지 않는다.** run3은 카드 2개만 세로로 오갔다.
- 스크롤 위치를 고정한다. 뷰포트에 잘린 카드는 shift score가 다르다(0.000819 / 0.000578 / 0.000101).
- 녹화 **직전마다** CPU 6x를 확인한다. 1차 측정은 3회 모두 스로틀링이 빠져 재측정했다.

## 측정 방법 메모

- **프레임 판정**: `PipelineReporter` 이벤트의 `args.frame_reporter.state`를 썼다 (`STATE_DROPPED` / `STATE_PRESENTED_PARTIAL` / `STATE_PRESENTED_ALL`). 최신 Chrome은 `DroppedFrame` 이벤트를 더 이상 내보내지 않는다. `ph: 'b'`(시작) 이벤트에만 `frame_reporter`가 붙으므로 `ph: 'e'`는 제외해야 하고, `id2.local`로 b/e를 짝지어야 프레임의 실제 구간을 얻는다. 페이지 레이어 트리(`layer_tree_host_id: 3`)만 세고 확장 프로그램 레이어 트리(`33`)는 제외했다. `STATE_NO_UPDATE_DESIRED`는 분모에서 뺐다.
- **호버-프레임 인과 판정**: partial/dropped 프레임의 `[b.ts, e.ts]` 구간 안에 호버 `Layout`의 `ts`가 들어 있는지로 판정했다. 프레임 시작 시각과 호버 시각을 단순 비교(±3ms)하면 프레임이 8~38ms에 걸쳐 있어 누락된다.
- **호버 상태 변화 수**: `LayoutShift`의 `impacted_nodes` 개수 합을 썼다. `EventDispatch`의 `mouseover`/`mouseout`은 카드 내부의 `img`·`h4`로 포인터가 옮겨갈 때도 발생해(회차당 26~38건) 실제 호버 상태 변화와 일치하지 않는다.
- **녹화 구간**: `metadata.modifications.initialBreadcrumb.window`.
- **렌더러 메인 점유**: 녹화 시작 지점의 239~264ms 태스크는 DevTools 자신의 `ScriptCatchup`(소스 런다운)이라 앱 비용에서 제외했다. 제외 전 점유는 6.8~8.5%p 더 높게 나온다.
